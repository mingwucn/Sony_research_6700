## Native program provenance

The native bootstrap can select a special target through a bounded version-file
test and saved-setting predicates; an explicit argument is another route. The
initializer's corresponding flag appends an explicit system-program filename
and load option. Exact packaged mount references identify the partition behind
that path. This supplies a concrete conditional source, independently of the
earlier warm-boot section gap. It does not identify the normal preloaded source
or establish the owner's current arguments, mode or boot behavior.

One fresh authored observer retained the exact 32,762,880-byte system member.
It rechecked the complete original package and decoded stream, all 1,000,017
physical envelopes and the entire selected member against accepted identities.
The image was read as inert bytes and never mounted.

The fixed-input filesystem model is FAT12, with two equal allocation tables.
Its 16-bit total-sector field exactly accounts for the member length. An older
conservative header predicate did not accept this form; that historical refusal
does not mean the image itself is malformed. New root-directory checks validate
all eight short/long-name pairs, including sequence, checksum, UTF-16 termination
and padding, and reject alias ambiguity. Only the explicitly named program
file was extracted.

The closed program is 13,805,416 bytes and satisfies the exact magic/version
predicate checked by the native module. An independent bit-addressed allocation
oracle walked all 843 clusters and compared every extracted byte, reproducing
the full file hash. Source identities, directory records, allocation segments,
program bytes, addresses and instruction evidence remain ignored and private.
This is an exact conditional program input, with no installed-body or normal
preload claim.

The native file-read loop copies bytes directly into the address-derived
destination. Under explicit assumptions that the current address and memory
base equal their independently retained packaged values, the program header's
two entry fields and API descriptor map inside this file. A separate entry-stub
literal points to the same later-entry value, and direct branch encodings reach
retained code prologues. This corroborates a local conditional layout. The full
211-slot API destination is present as zero bytes in the file; the native module
copies its source vector there before entry. That source has 194 relocation
entries and 17 literal-zero slots, so a slot is not automatically an implemented
function. No callback client is identified merely from that empty
destination, and current parameters, successful complete copying and actual
runtime publication remain unobserved.

The earlier native cache converter is now reviewed across its complete bounded
function: 81 instruction words, 12 internal branches, three direct calls and
three return sites. It performs guarded result validation after preparing a
candidate. Six system/barrier encodings are retained, with their architectural
result kept opaque because no retained primary definition establishes it.
Ordinary arithmetic does not prove successful translation or a usable pointer.
The LIRO program-address route uses its own memory-base arithmetic; the cache
function is not inserted into that separate call chain.

The retained modules also expose a distinct program-start gate after the first
initialization entry. A deferred route creates a proc callback and waits for a
completion; a power-management module writes the trigger path. The callback
does not validate the incoming content, and the reviewed order/error handling
does not establish a reliable readiness handshake. Program source, API-vector
publication, first initialization and deferred main entry must remain separate.
